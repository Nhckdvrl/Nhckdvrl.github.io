从论文集合到技术叙事

如何把大量 papers 重组为一篇能从头读懂的技术文章：定义可比较的分类轴，寻找有边界的共同数学结构，再用解释与证据连接方法之间的空白。

读一个新方向时，很容易积累一长串摘要：每篇解决什么问题、用了什么模块、提高了多少分。真正写作时，却仍然难以回答：这些方法为什么不同？差异来自假设、机制，还是实验设置？下一篇论文应该放在哪里？

技术 synthesis 的工作，是把论文中的知识重新组织成一条可推演的路径。读者沿着同一组问题前进，逐步理解一个方法为何出现、它改变了什么，以及解释到哪里必须停下来等待证据。

先限定问题，再扩大阅读

Topic 最好写成带约束的问题。例如，把“LLM multi-agent systems”收窄为：“在固定推理预算下，多个语言模型实例如何通过通信与验证，提高同一任务的完成率？”这样便能明确研究对象、资源约束和目标，也暂时排除训练期协作、竞争博弈等不同问题。

阅读可以从少量代表性工作展开，再沿引用关系补齐早期方法、相邻路线、负面结果和评测研究。每篇论文留下的记录应包括：任务与输入、可用信息、方法机制、预算、评价指标、核心证据、失效条件，以及对应的章节或实验位置。

每增加一批文献，检查是否出现现有框架无法解释的方法或结论。若仍有，就调整边界或分类。新论文大多只填充已有位置，是一个实用的阶段性停止信号；它不等于已经覆盖全部文献。

Taxonomy 的轴必须能被判定

好的 taxonomy 需要说明“依据什么分类”。“planning / reasoning / collaboration”容易重叠，因为它们可能同时描述一个系统。更可操作的做法，是从研究问题中提取可以逐项检查的设计变量。

以推理期协作为例，可以先选三个轴：

  • 信息可见性：一个 agent 决策时，能读到哪些原始输入、其他 agent 的输出与工具结果？区分全量共享、局部传递和独立求解。
  • 控制权分配：谁决定下一次调用、消息接收者与终止时机？记录固定流程、中心调度或分布式决策。
  • 验证信号来源：候选答案由模型互评、可执行测试，还是外部环境反馈来检查？一个系统可以使用多种信号。

这些轴分别描述信息、决策和证据，概念上可区分，实际设计中仍可能相互制约。分类单位也要固定：应当给具体的系统配置分类，不能假定一篇论文只有一种配置。把方法映射到这些轴后，再解释哪些组合常见、哪些缺少比较。

分类表里的空格只是尚未找到实例，不能直接当作 research gap。它也可能对应不可行的组合，或已有工作采用了不同术语。

用共同数学结构连接方法

数学抽象的作用，是让方法差异落在同一套符号里。对一个有限步、合作式、推理期多 agent 系统，可以写出下面的设计目标：

maximize_π E[R(y, y*)] subject to E[C(τ)] ≤ B

其中，输入 x 与参考目标 y* 来自任务分布；τ 是一次运行中生成、通信和工具调用的轨迹；π 表示系统的调用、通信与输出策略；y 是最终答案；R 是任务评分；C 是约定的成本，B 是预算。期望同时覆盖任务采样与系统随机性。y* 用于评测，不意味着推理时系统能访问它。

这个式子描述设计目标，不声称具体方法真的求解了该优化问题。成本也必须有明确定义：token 数、费用与延迟不能未经换算直接相加。这里采用平均预算；若应用要求每次运行都不能超支，就需要约束单条轨迹的成本。

在这一视角下，多数设计选择可以被问成同一个问题：它把额外计算花在哪里，又通过什么信息改变后续决策？独立采样把预算用于生成多个候选；互相批评增加跨候选的信息传递；测试反馈提供新的可观测证据；调度器决定何时值得继续调用。它们由此获得了共同的解释语言，但不因此具备相同的性能保证。

一个小例子：协作的收益来自哪里？

考虑代码生成。系统 A 让三个 solver 独立作答，再交给 selector 选择；系统 B 让一个 solver 写代码、一个 critic 提意见，最后修订。两者都使用多个模型实例，但通信方式和决策依赖不同。

如果 B 得分更高，可能来自有效反馈，也可能只是多用了 token，或者获得了 A 没有的测试信息。要解释结果，需要对齐底层模型、任务集合、工具权限和预算，并保留一个使用相同预算的单 agent 基线。

进一步可以分别移除 critic 反馈、加入独立重采样、替换为可执行测试反馈。比较成功率之外，还应记录成本、延迟、失败类型与重复运行的波动。消融会改变系统行为与资源消耗，因此也要报告这些变化，不能只列一个最终分数。

这时，“通信提高表现”才变成一个可以细查的机制假说：信息是否改变了错误答案？接收方是否能识别有效反馈？错误是否在 agent 之间传播？如果论文没有相应实验，就保留为待验证解释。

补齐 gap，也标明解释的边界

论文之间常缺三类连接：术语不同却指向相近机制；推导省略了中间步骤；实验设置不同导致结果无法直接比较。作者可以补上符号对照、展开推导条件，或解释比较为什么受限。

这里需要区分三种句子：“论文在某设置下观察到什么”“在明确假设下可以推出什么”“一个可能的解释是什么”。前者应能定位到证据，第二类需要给出推理过程，第三类应附上可能证伪它的实验。解释能减少理解成本，但不能填补尚不存在的实验结果。

例如，“critic 可能帮助 solver 发现局部错误”是机制解释；“多一个 critic 就会提高正确率”则需要额外条件和证据。写作时把这条边界留在正文里，比在结尾统一加一句 disclaimer 更有用。

最后，按读者的依赖顺序重写

初稿可以从问题、任务假设和最低限度的先修知识开始，再引入共同抽象；随后按设计选择展开方法，用对齐后的证据讨论取舍，最后指出尚未回答的问题。上面的例子只要求读者理解条件生成、期望与基本实验对照；不必为了显得统一，引入未实际使用的强化学习术语。

一个实用工作流是维护两份材料：一份按论文保存来源与证据，另一份按问题写正文。正文每节先提出读者此时会问的问题，再引入回答它所需的方法。完成后，把核心论断逐条接回来源、推导或假说，并检查符号是否一致、比较条件是否交代、结论是否超出了证据。

最终的检验很简单：暂时拿掉论文名称，文章是否仍有清楚的逻辑？再把来源放回去，每个重要判断是否都知道依据在哪里？前一个问题检查 narrative，后一个问题检查可信度。

选一个 topic，大量读 papers，建立 taxonomy，寻找共同数学与思想主线，再围绕读者的问题重组。真正值得写出来的，是论文之间那些经过解释、检验并标明边界的连接。
